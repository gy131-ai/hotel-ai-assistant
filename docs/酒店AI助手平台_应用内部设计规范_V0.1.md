## 2. 规范目标

本规范用于约束酒店AI助手平台下各应用的基础产品结构、交互方式和平台接入规则。

总体原则：

> 平台统一外壳、身份和交互规则；应用保留自己的业务流程和主题特征。

应用设计不要求完全一致，但必须保证用户在不同应用之间切换时，对酒店身份、任务、消息、返回方式和数据归属具有一致认知。

---

## 3. 必须统一的部分

### 3.1 应用顶部结构

每个应用顶部统一包含：

```text
返回酒店AI助手
应用名称
当前酒店名称 ⌄
```

规则：

- 返回时回到酒店AI助手首页；
- 酒店切换使用平台统一组件；
- 应用不维护独立酒店列表；
- 编辑、上传、生成过程中切换酒店，需要保存或退出确认。

### 3.2 应用首页结构

每个应用进入后，应首先回答四个问题：

1. 当前情况怎么样？
2. 有什么需要处理？
3. 最近产生了什么结果？
4. 下一步可以做什么？

建议统一框架：

```text
应用首页
├── 当前状态
├── 待处理任务
├── 核心操作
├── 最近结果
└── 应用内历史记录
```

不同应用可以根据业务特征调整顺序，但必须有一个明确的主操作。

| 应用 | 当前状态 | 主操作 | 最近结果 |
|---|---|---|---|
| 营点AI | 本月剩余12次 | 开始创作 | 最近生成的图片、视频 |
| 账清AI | 今日对账未完成 | 上传账单 | 最近一次对账结果 |
| 行李寄存 | 当前6件寄存中 | 新增寄存 | 最近领取记录 |
| 酒店资讯 | 今日新增8条 | 查看资讯 | 最近收藏内容 |
| 碰碰贴 | 3台在线、1台离线 | 管理设备 | 最近设备记录 |
| 吐槽码 | 今日2条反馈 | 查看反馈 | 最近处理结果 |

### 3.3 任务规范

应用内部负责完整任务列表，平台首页只显示最高优先级任务。

每个任务必须具备：

```text
任务标题
任务说明
所属酒店
优先级
处理状态
创建时间
处理入口
```

任务状态统一为：

```text
待处理 → 处理中 → 已完成 / 已取消
```

要求：

- 平台点击任务，可以直接进入应用的具体处理页面；
- 应用完成任务后，必须同步更新平台；
- 不要让用户进入应用后重新寻找对应事项；
- 仅“需要用户采取动作”的事项才创建任务。

### 3.4 消息规范

应用内部可以保留完整消息记录，平台只聚合重要消息。

适合产生消息的场景：

- 图片或视频生成完成；
- 对账文件处理完成；
- 出现重要异常；
- 收到严重反馈；
- 设备离线或恢复；
- 套餐即将到期。

不适合产生消息的场景：

- 普通页面访问；
- 用户每次保存；
- 普通数据刷新；
- 没有用户价值的系统日志。

消息阅读和任务完成必须分别处理。

### 3.5 结果归属

所有业务结果保留在应用内部：

- 营点AI：图片、视频、文案、草稿；
- 账清AI：每日对账结果、异常记录；
- 行李寄存：寄存和领取记录；
- 酒店资讯：资讯、收藏、阅读记录；
- 吐槽码：反馈内容和处理记录；
- 碰碰贴：设备与触达数据。

平台不建设统一“作品”或“成果”频道。

每条结果至少绑定：

```text
hotel_id
app_id
creator_user_id
result_id
created_at
```

## 4. 平台能力使用要求

### 4.1 酒店 Context

应用按需读取酒店 Context，不要求所有应用读取全部字段。

例如：

- 营点AI读取品牌、卖点、房型、品牌色；
- 账清AI读取PMS、收款方式、OTA渠道；
- 行李寄存读取寄存规则和联系方式。

应用需要补充公共酒店资料时，应写回平台 Context，避免每个应用保存一份重复信息。

应用专属配置仍保留在应用内部。

### 4.2 素材库

应用可以：

- 读取当前酒店的公共素材；
- 上传素材；
- 将业务成果保存为应用内结果；
- 经用户确认后，将成果加入酒店公共素材库。

应用不能默认将所有中间文件写入共享素材库。

### 4.3 应用权益

应用进入时需要校验：

- 是否开通；
- 是否在有效期；
- 剩余额度；
- 是否允许执行当前操作。

权益不足时统一展示：

```text
权益说明
当前使用情况
购买或续费入口
返回酒店AI助手
```

## 5. 允许应用差异化的部分

以下内容不需要平台强制统一：

- 具体页面数量；
- 业务操作流程；
- 结果展示形式；
- 应用内部导航；
- 专属数据字段；
- 主题辅助色；
- 是否使用对话式交互；
- 是否包含AI生成过程。

例如：

- 营点AI可以更偏创作工具；
- 账清AI可以更偏数据表格和异常处理；
- 行李寄存可以更偏扫码和快速登记。

整体应保持同一套字体、间距、按钮、卡片和状态反馈规范。

账清AI可以使用绿色作为业务主题色，营点AI可以使用蓝色，但不能形成两个完全不同的产品体系。

## 6. 统一页面状态

每个应用至少需要设计以下状态：

```text
首次使用
正常状态
无数据
加载中
处理进行中
处理成功
处理失败
网络异常
权益不足
酒店资料不足
应用已到期
```

资料不足时，不只提示“资料不完整”，而应明确说明缺少哪些资料、为什么需要，以及用户可以采取的动作。

示例：

> 生成酒店品牌宣传图需要酒店Logo和品牌色。

```text
[立即补充]  [暂不使用酒店资料]
```

---

## 7. 应用最小页面模板

一个应用最少可以由四类页面组成：

```text
1. 应用首页
   当前状态、主要任务、核心操作、最近结果

2. 核心业务页
   完成上传、创作、登记、对账等操作

3. 结果/历史页
   查看应用产生的完整业务成果

4. 应用设置页
   应用专属规则、渠道、模板或设备配置
```

酒店基础资料、公共素材、用户信息和订阅管理不在应用内重复建设，只调用平台能力。

---

## 8. 应用接入验收

每个应用接入平台前至少确认：

- 能接收平台传入的 `user_id` 和 `hotel_id`；
- 数据严格归属于当前酒店；
- 可以从应用返回酒店AI助手；
- 可以调用平台酒店切换器；
- 可以向平台提供一条应用摘要；
- 可以向平台同步任务状态；
- 可以向平台发送重要消息；
- 平台任务可以直达应用具体页面；
- 应用结果保留在应用内部；
- 不重复建设酒店、用户和公共素材体系。

---

## 9. 设计结论

> 入口和身份由平台统一，状态和待办向平台输出，详细流程和业务结果留在应用内部。
